# Supporting Crates

The remaining `Cargo.toml` workspace members. Each is small and single-purpose; the ones whose behavior is explained by a concept link to it rather than repeating it.

| Crate | Job |
|---|---|
| `error_trace`, `error_trace_derive` | The error type and its derive macro, carrying context across the FFI boundary. Conventions in [../best-practices/rust-error-handling.md](../best-practices/rust-error-handling.md). |
| `proto_generator`, `proto_utils` | Generate and support the Rust types for `protobuf/database_driver_v1.proto`. The contract itself is [../../concepts/core-and-bridge-split.md](../../concepts/core-and-bridge-split.md). |
| `sf_params_spec`, `sf_params_codegen` | The single definition of every connection parameter, and the `param_defs_export` binary that emits each wrapper's view. See [../../concepts/connection-parameters.md](../../concepts/connection-parameters.md). |
| `sf_mini_core`, `sf_mini_core_static` | A deliberately minimal library used to prove dynamic-library loading works. See below. |

## `sf_mini_core` — the loading probe

Not part of the Universal Driver. It is a minimal Rust dynamic library shipped **alongside the existing legacy drivers** to de-risk loading Rust code into them before real functionality follows. Its purpose is to generate telemetry on dynamic-library loading across platforms, validate the mechanism, and surface compatibility problems early.

It exports one C-compatible function, `sf_core_full_version`, returning a static version string the caller must not free. If that call succeeds, the library loaded.

`sf_mini_core` is `["cdylib", "rlib"]`; `sf_mini_core_static` is a `staticlib` wrapper around it for callers that link statically.

Packaging is its own path, not the normal cargo build:

```bash
export PLATFORM=macos-aarch64   # or linux-x86_64-glibc, windows-x86_64, ...
./scripts/package_minicore.sh
```

That generates the C header with cbindgen, builds both variants, and writes a distributable archive under `build/`. `scripts/upload_minicore.sh` publishes it.

## Gotchas

- **`sf_mini_core` has no dependency on `sf_core`** despite the name and the `sf_core_full_version` export. Do not reach for it expecting driver behavior — it is a loading probe.
- The generated outputs of `proto_generator` and `sf_params_codegen` are regenerated by pre-commit hooks; edit the source crate, not the output.
